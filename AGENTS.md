# Работа с Pet-Travel

## Область ответственности

- Работать только с этим репозиторием. Основное задание — `docs/CODEX_TASK.md`; актуальные указания владельца имеют приоритет.
- Разрабатывать приложение, его схему данных, миграции, тесты и документацию.
- Владелец отвечает за DevOps. Без отдельного запроса не создавать Docker/Compose, CI/CD workflows, reverse proxy, Kubernetes/Helm, Terraform, Ansible, мониторинг и деплой. Не менять Windows, WSL, сеть и внешние серверы.
- Сохранять назначение: владельцы, ситтеры, питомцы, статьи, общение. Не добавлять фиктивные рейтинги, отзывы, оплату, бронирование и транспортные услуги.

## Код и данные

- Node.js указан в `.nvmrc`. Установка — `npm ci` из корня; один workspace lock-файл.
- API и WebSocket используют одну серверную сессию. Проверять роль, принадлежность данных, Origin, CSRF и входные поля на сервере.
- Не помещать секреты и реальные персональные данные в Git, логи, снимки экрана, описания PR или frontend. Не выводить `.env` и URL с паролями.
- В логи передавать только операционные поля из allowlist `server/src/logger.js`.
- Существующие применённые миграции не редактировать. Добавлять следующую миграцию; избегать скрытого удаления/слияния данных и `sync({force:true})`.
- Не выполнять `db:drop` на существующей или неизвестной БД. Тесты допускаются только в специально выделенной БД `_test`; удалять можно только схему, созданную текущим тестом.
- Сохранять полезные тексты и URL девяти статей; продуктовые обещания должны соответствовать API. Указывать лицензии новых медиа.

## Проверки и Git

- Изменения исходников проверять подходящими `npm run lint`, `npm test`, `npm run build`. Для API/БД/чата запускать интеграционные тесты; для пользовательских сценариев — Playwright. Для правок только документации достаточно проверки ссылок и diff.
- Не объявлять пропущенные тесты успешными. Записывать среду, команды и ограничения в `docs/TESTING.md` при новой приёмке.
- Работать отдельной веткой от `develop`, отправлять PR. Правила — `docs/BRANCHING.md`.
- Не переписывать опубликованную историю, не делать force-push, не обходить защиту. Сохранять архивные refs перед выводом старых веток из работы.
- В PR описывать проблему, итоговое поведение и фактическую проверку. Инфраструктурные решения оставлять владельцу в `docs/DEVOPS_HANDOFF.md`.
