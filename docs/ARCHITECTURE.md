# Архитектура и контракт приложения

## Компоненты

React SPA находится в `client`, Express API — в `server`. Vite используется для разработки и сборки, а собранный `client/dist` может отдавать сам Express. HTTP и WebSocket работают на одном сервере. Внешних SaaS, Redis и файлового хранилища приложение не требует.

```mermaid
sequenceDiagram
    participant B as Браузер
    participant A as Express / ws
    participant P as PostgreSQL
    B->>A: GET /api/auth/session
    A->>P: Прочитать / сохранить сессию
    A-->>B: user, csrfToken + HttpOnly cookie
    B->>A: POST /api/auth/login (Origin, CSRF)
    A->>P: Проверить bcrypt, заменить ID сессии
    A-->>B: user, новый csrfToken + cookie
    B->>A: PUT /api/profile / CRUD /api/pets
    A->>P: Проверить владельца и записать данные
    B->>A: Upgrade /ws (Origin, cookie)
    A->>P: Проверить сессию и пользователя
    B->>A: message: recipientId, text
    A->>P: Сохранить Message
    A-->>B: message с ID и временем; доставка участникам
```

`AuthProvider` восстанавливает сессию, хранит только публичные поля пользователя и CSRF-токен в памяти. Токены/пароли не сохраняются в localStorage. Начальный запрос разделяется между эффектами React StrictMode, чтобы не создавать конкурирующие анонимные сессии. Redux удалён: для текущего объёма достаточно Context и локального состояния экранов.

## Модели и постоянные данные

| Таблица | Связь и назначение | Использование сейчас |
|---|---|---|
| Users | Имя, почта, bcrypt-хэш, роль; один профиль выбранной роли | Регистрация, вход, профиль, контакт чата |
| ParentProfiles | `UserId` уникален; страна, город, описание дома и ухода | Свой профиль владельца |
| SitterProfiles | `UserId` уникален; опыт, статус и 7 флагов видов животных | Свой профиль ситтера |
| Pets | `ParentProfileId` → ParentProfiles; имя, возраст, тип, фото | CRUD владельца |
| Messages | `senderId`, `recipientId` → Users; текст и время | Приватная переписка, индекс по участникам и ID |
| session | `sid`, `sess`, `expire`; индекс срока жизни | PostgreSQL-хранилище HTTP/WS-сессий |
| Verifications | Исходная связь с Users | Сохранено; процесс верификации не реализован |
| ParentReviews | Исходные связи с профилями | Сохранено; API и интерфейса нет |
| SitterReviews | Исходные связи с профилями | Сохранено; API и интерфейса нет |
| AppReviews | Исходная связь с Users | Сохранено; API и интерфейса нет |
| SequelizeMeta | Имена применённых миграций | Управление схемой |

Восемь старых миграций сохранены. Девятая добавляет Messages и session, уникальность `lower(email)` и профилей, ограничения ролей/возраста/длины сообщения. Даты первого отсутствия в профиле владельца стали необязательными. Неиспользуемые старые поля, дополнительные фотографии и данные отзывов не удалены. `raiting` остаётся историческим именем поля, а не пользовательским рейтингом.

Мигратор выполняет ожидающие миграции в одной транзакции с advisory lock. Дубликаты email/профилей, неправильные роли, недопустимый возраст или пустая обязательная связь могут остановить обновление; изменения откатятся. Он не исправляет неоднозначные данные автоматически. Приложение при старте не делает `sync` и не запускает миграции самостоятельно.

## HTTP API

Все тела — JSON. Успешные GET/PUT возвращают 200, создание — 201, удаление/выход — 204. Для изменяющих `/api` запросов нужны разрешённый `Origin`, cookie и `X-CSRF-Token` из `/api/auth/session` или последнего успешного входа. После входа и регистрации токен меняется.

| Метод и путь | Доступ | Запрос / ответ |
|---|---|---|
| GET `/health/live` | Публичный | 200 `{status:"ok"}` при работающем HTTP-процессе |
| GET `/health/ready` | Публичный | Реальные запросы к Users, Messages, session; 200 ready / 503 not_ready |
| GET `/version` | Публичный | Имя и версия приложения |
| GET `/api/auth/session` | Публичный | `{user:null или publicUser, csrfToken}` |
| POST `/api/auth/signup` | CSRF | `name,email,password,role` → user и csrfToken |
| POST `/api/auth/login` | CSRF | `email,password` → user и csrfToken |
| POST `/api/auth/logout` | CSRF | Удаление сессии, очистка cookie, закрытие её WebSocket |
| GET `/api/profile` | Сессия | `{user,profile}`; профиль может быть null |
| PUT `/api/profile` | Сессия | Создание/обновление собственного профиля выбранной роли |
| GET `/api/pets` | parent + профиль | `{pets:[]}` только своих питомцев |
| POST `/api/pets` | parent + профиль | `petName,petAge,type,petPhoto` → `{pet}` |
| PUT `/api/pets/:id` | Владелец питомца | Те же поля → `{pet}` |
| DELETE `/api/pets/:id` | Владелец питомца | 204 |
| GET `/api/chat/contacts/:id` | Сессия | `{user:publicUser}`; отсутствующий/свой ID → 404 |
| GET `/api/chat/messages/:id?before=...` | Участник диалога | До 50 сообщений по возрастанию ID, `{messages,hasMore}` |

`publicUser` содержит только `id,name,surname,role,mainPhoto`; email, хэш, социальные контакты не раскрываются. Для history `:id` — ID собеседника, `before` — ID самого раннего уже загруженного сообщения. На ровно 50 сообщениях `hasMore` может потребовать ещё один пустой запрос.

Профиль: общие поля `name,surname,mainPhoto,country,city` (пустые surname/mainPhoto допустимы). У владельца дополнительно `title,introduction,location,responsibilities`; у ситтера `aboutMe,status,cats,dogs,reptiles,fish,smallPets,horses,birds`. PUT ожидает полный разрешённый набор, неизвестные поля отвергаются. Роль, email и владельца записи этим API изменить нельзя.

Пароль регистрации: от 12 символов, не более 72 UTF-8 байт (граница bcrypt). Имя до 80 символов, email до 254 и нормализуется к нижнему регистру. Возраст питомца — целое 0–100 либо null; виды `cat,dog,bird,fish,reptile,smallPet,horse,other`. Фото — пустая строка или HTTPS URL до 255 символов, без встроенного логина/пароля. Сервер не скачивает фото: его загружает браузер посетителя.

Ошибки: 400 валидация/JSON, 401 нет сессии/неверный вход, 403 роль/Origin/CSRF, 404 чужой питомец/контакт, 409 конфликт или незаполненный профиль, 413 тело >32 KiB, 429 лимит входа, 500 обезличенная ошибка. Центральный обработчик добавляет `requestId` и при валидации `fields`. Каждый HTTP-ответ имеет `X-Request-ID`. Неизвестный API-маршрут после авторизации возвращает JSON 404; анонимный — 401. SPA-страница 404 отображается клиентом, её HTML-оболочка имеет HTTP 200.

## WebSocket `/ws`

Подключение требует действующую cookie-сессию и точное совпадение Origin. Сервер отправляет `{ "type": "ready" }`. Клиент отправляет:

```json
{ "type": "message", "recipientId": 2, "text": "Здравствуйте!" }
```

Сервер определяет отправителя из сессии, сохраняет текст и отвечает обоим участникам `{type:"message",message:{id,senderId,recipientId,text,createdAt,updatedAt}}`. При ошибке — `{type:"error",error:"..."}`. Поле `senderId` от клиента отвергается.

Лимиты: текст 1–2000 символов, пакет до 16 KiB, 30 сообщений в минуту на соединение, максимум 5 соединений пользователя. Ping/pong каждые 30 секунд. Перед записью и доставкой проверяется сохранённая сессия. При выходе/замене сессии открытые соединения закрываются. Клиент переподключается с задержкой 1–15 секунд и восстанавливает историю через HTTP. Сообщение подтверждается после записи в БД; если подтверждение потеряно, пользователь проверяет историю перед ручной повторной отправкой. Гарантии exactly-once и read receipts нет.

Доставка онлайн рассчитана на **один процесс API**: подписки находятся в памяти. PostgreSQL хранит сессии и историю, но не распределяет WebSocket-события между процессами. Расширение на несколько реплик потребует отдельного решения, а не только sticky sessions.

## Защита и границы

Порядок middleware: request ID → Helmet → публичные health → CORS → JSON/session → Origin+CSRF → auth → проверка роли/владения. Сессия живёт до 7 дней; cookie HttpOnly, SameSite=Lax, Secure в production. Изменение `SESSION_SECRET` аннулирует существующие cookie. Смена/восстановление пароля и удаление аккаунта пока отсутствуют.

SQL выполняется через Sequelize/параметры; произвольный HTML не рендерится. Helmet ограничивает ресурсы, фото разрешены с HTTPS. Auth-лимит — 25 попыток за 15 минут на IP (100 в тестовом режиме), хранится в памяти. ID контакта не является секретом: авторизованный пользователь может запросить минимальную карточку любого существующего ID и написать ему. Согласие на первый контакт, блокировка и модерация — будущая продуктовая работа.
