# Передача Pet-Travel DevOps-инженеру

**Точка передачи:** ветка `main`, проверенный код [45b30f5509850c11549ea4bb59f82d85715e5166](https://github.com/Andrew-Kotlov/Pet-Travel/commit/45b30f5509850c11549ea4bb59f82d85715e5166). Последующие коммиты передачи добавляют документацию и снимки. Запуск: `npm ci` → `.env` → `npm run db:migrate` → `npm run build` → `npm start`. Пройдены lint, сборка, 10 unit API, 18 React, 21 PostgreSQL/WS/migration и 5 E2E; оба dependency audit — 0 уязвимостей. [Условия проверки](TESTING.md).

Ограничения: один процесс API для онлайн-чата; контакт по ID; нет каталога, бронирования, оплаты, восстановления пароля и готового процесса отзывов. Production TLS/reverse proxy и Linux-сигналы в реальном развёртывании ещё не проверены.

**Первый конкретный шаг:** воспроизвести запуск `main` в своей Ubuntu/WSL2 по [DEVELOPMENT](DEVELOPMENT.md) и получить HTTP 200 от `http://127.0.0.1:3001/health/ready`. Это исходная проверка приложения перед первой контейнеризацией.

## Состав и порты

| Компонент | Запуск / артефакт | Порт по умолчанию | Постоянные данные |
|---|---|---|---|
| React frontend | `npm run build` → `client/dist` | Отдаёт Express 3001 | Нет; статическая сборка |
| Node.js API + WS + static | Из корня `node --env-file=.env server/src/index.js` | `HOST:PORT`, 127.0.0.1:3001 | В PostgreSQL |
| PostgreSQL 17 | Подготавливает владелец среды | 5432 | Все аккаунты, профили, питомцы, сообщения, отзывы legacy, сессии, миграции |
| Vite для разработки | `npm run dev` | 127.0.0.1:5173 | Нет; в production не нужен |
| Сервер E2E | Автоматически `npm run test:e2e` | 127.0.0.1:3187 | Временная схема отдельной `_test` БД |

Клиент и сервер можно отдавать с одного публичного origin. Это упрощает cookie, CORS и `/ws`. API не требует отдельного внешнего сервиса. Проверенные версии: Node 24.22.3, npm 12.2.3, PostgreSQL 17.12. Воспроизводимость npm обеспечивает один корневой lock-файл.

## Переменные окружения

Корневой `.env.example` — шаблон; `.env` и `.env.test` игнорируются Git. Переменные процесса имеют приоритет над env-файлом. На frontend не передаются DB URL и секреты; публичных `VITE_*` параметров сейчас нет.

| Переменная | Значение / назначение |
|---|---|
| `NODE_ENV` | development/test/production; по умолчанию development. Production требует HTTPS origin и включает Secure cookie |
| `HOST` | Интерфейс HTTP, по умолчанию 127.0.0.1. Для будущего контейнера выбирает владелец |
| `PORT` | HTTP и WS, по умолчанию 3001; 0 допускается для тестового случайного порта |
| `DATABASE_URL` | Обязательный `postgresql://...`; рабочая БД, не тестовая |
| `SESSION_SECRET` | Обязательный случайный секрет минимум 32 символа; генерировать отдельно для каждой среды. Смена аннулирует cookie |
| `ALLOWED_ORIGINS` | Точные origins через запятую, без пути, wildcard и завершающего `/`. В production только HTTPS |
| `TRUST_PROXY` | Число доверенных переходов 0–5; по умолчанию 0. Согласовать с реальной топологией и закрыть прямой обход proxy |
| `DB_SSL` | true/false. При true проверяется сертификат PostgreSQL; при необходимости доверенный CA передаёт среда Node |
| `LOG_LEVEL` | info/error/silent; info по умолчанию |
| `API_PROXY_TARGET` | Только dev Vite: адрес API, если он отличается от localhost + PORT; не встраивается в клиентскую сборку |
| `TEST_DATABASE_URL` | В `.env.test`, отдельная локальная тестовая БД с именем `_test`; права создания схем |
| `ALLOW_DEMO_SEED` | Только явное true разрешает вымышленные данные вне production |
| `DEMO_PASSWORD` | Пароль demo-аккаунтов, 12–72 UTF-8 байта; хранить локально, seed не логирует |
| `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` | Необязательно: путь к уже установленному Chromium/Chrome для E2E |

Для новых окружений подготовить отдельные credentials и роль БД. Миграции требуют DDL; обычная работа — доступ к таблицам/sequence и обновление session. Конкретные grants и безопасное хранение секретов определяет DevOps. Нельзя запускать рабочую среду с `NODE_ENV=test`: там повышен auth-лимит.

## Готовность, завершение и журналы

- `/health/live`: HTTP 200, процесс способен отвечать; состояние БД не проверяет.
- `/health/ready`: запросы к Users, Messages и session; 200 ready либо 503 not_ready. Это не полный аудит схемы, миграции обязательны до старта трафика.
- `/version`: имя `pet-travel`, версия `2.0.0`, без секретов.
- SIGTERM/SIGINT: readiness переключается в not_ready, WS закрываются, HTTP прекращает принимать новые соединения; через 10 секунд оставшиеся HTTP-соединения принудительно закрываются; затем закрываются пулы PostgreSQL.
- Успешное завершение — код 0; некорректная конфигурация/занятый порт/ошибка запуска — код 1. При недоступной БД HTTP может подняться с readiness 503: рестарт не заменяет исправление подключения.
- В будущей среде лучше запускать Node напрямую как основной процесс и дать более 10 секунд на остановку. Не полагаться на пересылку сигналов через оболочку/npm.
- Логи — JSON в stdout; time, level, event, requestId, method, status, durationMs и port. Тела, URL, cookie, токены, email, ID пользователей и текст сообщений не пишутся. Поле `X-Request-ID` позволяет сопоставить HTTP-ответ и запись журнала.

SIGINT/SIGTERM обработаны в коде; в Windows проверены `runtime.close()`, повторный запуск и штатная IPC-остановка локального launcher. Реальный цикл сигналов Linux/контейнера проверяет владелец в своей среде.

## Данные, обновления и восстановление

Сохранности требует **PostgreSQL целиком**, включая Messages и SequelizeMeta. Session содержит чувствительное состояние входа; резервные копии нужно защищать как пользовательские данные. Фотографии интерфейса — исходники в Git; пользовательские фото представлены внешними URL, приложение их не копирует. Загружаемого файлового контента пока нет.

До применения миграции к существующей базе нужен проверенный backup/restore и пробное обновление копии. Новая миграция намеренно останавливается при дубликатах и недопустимых legacy-данных. Нет автоматического down, удаляющего сообщения; откат релиза нельзя приравнивать к откату схемы. Исправление выполняется отдельной проверенной миграцией вперёд либо согласованным восстановлением. Не удалять базу ради успешного запуска.

У приложения два пула (Sequelize и session), до примерно 20 соединений на один процесс при настройках по умолчанию. Лимиты и достаточный timeout healthchecks нужно выбирать с учётом БД и нагрузки. Нагрузочный профиль ещё не измерен.

## Требования к будущей инфраструктуре

Готовые конфигурации здесь не создавались. При самостоятельной реализации учесть:

1. **Контейнеризация:** воспроизводимая сборка с dev-зависимостями; runtime с production-зависимостями и `client/dist`; запуск непривилегированным пользователем; секреты вне образа; прямой процесс Node; отдельный этап миграций; постоянное хранилище БД.
2. **Reverse proxy/TLS:** один публичный HTTPS origin, `/api`, WebSocket Upgrade на `/ws`, корректный Host/Origin, доверенная цепочка forwarded-заголовков, timeout длиннее heartbeat 30 секунд. Статические файлы можно отдавать отдельно, сохранив SPA fallback и реальные `/api`/health.
3. **CI:** `npm ci`, lint, unit/frontend, build, отдельная PostgreSQL `_test`, integration, браузерные зависимости и E2E, dependency audit. Не подключать production-секреты к тестам. Сохранять отчёты без реальных данных.
4. **Эксплуатация:** readiness/liveness, частота 5xx, задержки и ошибки БД/WS, ротация stdout и контролируемый доступ к журналам; backup с проверкой восстановления. Метрики и мониторинг ещё не настроены.
5. **Масштабирование:** начать с одного процесса API. Для нескольких реплик потребуется доставка событий между процессами и распределённый rate limit; PostgreSQL-сессий самих по себе недостаточно.

Перед открытием для реальных пользователей отдельно определить процесс восстановления аккаунта, удаления данных, модерации и нежелательных контактов. Эти пользовательские функции не реализованы текущим инфраструктурным заданием.
